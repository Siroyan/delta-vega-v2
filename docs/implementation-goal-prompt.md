## アーキテクチャ

- システム全体はPorts and Adapters、表示側はMVP。
- 計測・周回・制御の中核をArduino、FreeRTOS、LVGL、MQTTから独立させ、PC上でテスト可能にする。
- 状態更新の責任者を明確にし、タスク間の共有状態・イベントの扱いを設計する。
- LVGL操作はUIの実行文脈に集約する。
- 計測、電装、GPS、通信、保存の状態を独立して扱う。
- EEZ生成コードを直接編集せず、必要な画面変更はEEZプロジェクトに反映して再生成する。
- 現在の承認済みデザインを保ち、Settingsや取消操作など必要な機能を追加する。
- docs/architecture.mdの配置・タスク・保存形式は設計案なので、根拠があれば改善してよい。変更理由を記録する。
- 可読性・保守性・拡張性を保ち、必要な境界に適切な抽象化を設ける。

## 車速・GPS

- Tab5がM5BusのGPIO・UARTから直接取得する。
- 車速はリードスイッチ。車輪周長1.03 m、1回転1パルス。
- パルスを正しく累積し、チャタリング対策と速度計算を実装する。
- GPSはGT-502MGG-N。測位状態・有効性・鮮度を扱う。
- 平均速度は、計測開始後の車輪パルス積算距離÷経過時間。停止時間を含める。
- 未取得・古い値と、有効な速度0を区別する。
- コース背景と実GPS位置の座標変換・現在位置表示を実装する。

GPIO割り当て：

- 車速入力：GPIO16
- GPS RX：GPIO7（GPS TXから受信）
- GPS TX：GPIO6
- 電装出力：GPIO45
- ECU始動パルス：GPIO48

実装前に公式ピン表・回路図と照合し、競合があれば根拠を示して修正してよい。

## レース計測

- 7周。
- START TIMINGの手動操作で開始し、現在周回1/7、経過時間0とする。
- スタート地点は位置確認用で、自動開始には使わない。
- 周回更新地点の有効通過で周回を更新する。
- 6回の更新で7/7となり、その後、指定ゴールの通過で完走する。
- 1〜6周目のゴール通過では完走しない。
- GPS自動ラップとMANUAL LAP +1を実装し、同じ通過の二重加算を防ぐ。
- 経過時間は単調増加時刻で管理し、NTP補正や描画遅延で変動させない。
- 電装OFFでもレース計測を継続する。
- 完走前の計測取消を可能にする。取消後は開始待ちへ戻り、新たに開始できる。
- 完走結果は保持し、完走後の再計測機能は不要。

初期座標：

- スタート：緯度36.530654、経度140.227998
- 周回更新：緯度36.532766、経度140.226269
- ゴール：緯度36.534443、経度140.225411

3地点は別々の設定として管理し、Settingsから変更可能にする。近似座標なので、通過判定の範囲・方向・重複抑制なども調整可能な構造にする。判定方式や暫定閾値は根拠とともに記録する。

## TARGETとSettings

- 全体TARGETの初期値は42:00。
- 1〜7周目のTARGET初期値は各06:00。
- 大会制限時間39:16と、暫定TARGET42:00を混同しない。
- 全体・各周TARGETと3地点をSettingsから編集・保存できるようにする。
- 計測中の設定変更は禁止し、UIとアプリケーションの双方で拒否する。
- 設定値を処理や生成画面に分散して埋め込まない。
- 画面に残り時間を追加せず、経過時間とTARGETを表示する。

## 電装・ECU始動

- 電装制御の対象はエンジン系電装のみ。Tab5・GPS・車速計測は電装OFFでも動作する。
- 暫定仕様はHIGHで電装ON、LOWでOFF。極性を変更可能にする。
- 起動・再起動時は電装OFFとし、明示的なON操作まで維持する。
- 電装ONからECU準備完了まで暫定1000 ms待ち、その間は点火ボタンを無効にする。
- 点火操作でECU向けGPIOをLOW→HIGH→LOWにする。HIGH時間は暫定1000 ms。
- 電装ONの1サイクルにつき始動指令は1回のみ。操作受理時にボタンを無効化し、中核でも重複を拒否する。
- 電装OFF→ONで新たな始動が可能になる。
- 電装OFF時は準備待ち・パルスを解除する。
- 待ち時間・パルス中も計測とUIを継続する。
- スターター・点火・自動停止はECUと車両側が担当する。Tab5による早期停止は電装OFFのみ。
- 電装・エンジンの実状態を確認する信号はない。指令状態を実運転状態として表示しない。
- ECU待ち時間とパルス幅は後日確認予定の暫定値として明記する。
- ファームウェア起動前・リセット中のOFF維持には回路側の対応も必要であり、ソフトウェアだけで保証したと扱わない。

## 保存・通信・時計

- 計測中のmicroSD保存は必須。
- MQTTに倣った項目を保存し、取消した記録も保持する。
- SD未挿入・書込失敗は警告し、計測・表示・制御を継続する。
- 初期実装では通信断中データの自動後送信と再起動後の計測復元は不要。
- AWS IoT送信機能は旧版の接続先・トピック・JSON項目・500 ms周期を出発点に実装する。改善に必要なら変更してよい。
- AWSへの実接続検証はスキップする。証明書・Wi-Fi設定は後でユーザーが準備する。
- 未設定・通信断でも起動、計測、表示、保存を継続できるようにする。
- 時計とNTP同期状態を実装する。未同期・同期済み・同期後の継続状態を区別する。
- 走行プラン解析・受信は将来機能とし、初期実装には含めない。

## 検証環境と完了条件

実機は接続してある。microSDは挿入済みだが、GPS・リードスイッチ・電装回路・ECUは未接続で、ほぼTab5単体。

- 中核の計測・周回・取消・設定・制御状態をPC上の意味のあるテストで検証する。
- 未接続の入力は模擬入力で検証する。通常動作では模擬値を実測値として表示しない。
- PlatformIOビルドを成功させる。
- 接続されたTab5へ書き込む。
- シリアルモニタで起動、リセット、例外、実行時エラーを確認する。
- microSDに実際に記録できることを確認する。
- 画面の目視確認はユーザーが行う。目視・未接続機器・AWS接続を検証済みと主張しない。
- 障害や未検証事項は、再現条件・ログ・残作業とともに記録する。
- 仕様書と設計書を実装に合わせて更新する。

## GitとPR

- devから実装用ブランチを作る。
- 必要なら複数ブランチを使用してよいが、最終的に一つへ統合する。

- 実装内容とアーキテクチャ
- 検証結果、実機書き込み・シリアル・microSD確認結果

- ユーザー指定の暫定値と、後日確認する項目
- 未検証の機能と残る実機評価事項
- 既存仕様・通信形式から変更した点と理由
