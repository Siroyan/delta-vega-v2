# タッチ応答遅延の調査と検証

## 確認できた原因

従来の実装は、Arduinoの同じ`loop()`内で`M5.update()`によるタッチ取得と`lv_timer_handler()`による描画を順番に実行していた。実機で画面遷移を繰り返すと、LVGL処理が最大約319 msかかり、その間タッチを読めなかった。

さらにEEZ生成の画面遷移は200 msのフェードだった。使用中のLVGL 9.2.2はアニメーション中（`prev_scr != NULL`）に入力処理を返すため、その間のタップを受け付けない。Tab5で使うM5GFXのGT911ドライバーも、読み取り間隔が128 ms以上空くと古いタッチデータを破棄する。この組み合わせで、短いタップを取りこぼせることをコードと実機の処理時間から確認した。

毎回の画面更新で、変化していないLED色や文字色などを再設定していたことも確認した。変更前の静止画面では5秒あたり約196～200回の描画転送が発生していた。

## 対策

- タッチ取得を独立したFreeRTOSタスクで約5 msごとに行い、押下・解放をキューに保持する。描画が長引いても短いタップの遷移をLVGLに渡せるようにした。
- EEZの画面切替テンプレートを即時切替に変更し、遷移中の入力停止をなくした。
- 状態が変わったウィジェットだけを更新し、不要な描画を減らした。タッチごとのシリアル出力も削除した。
- シリアルモニターから`perf`を送ると、前回の表示以降の最大タッチ取得間隔、LVGL処理時間、入力配達遅延、キューの取りこぼし数などを表示する。

## 実機での確認結果と残る確認

修正後、Tab5単体で12回のSettings往復と24回の数値欄オープンをシリアル操作で実施し、起動・画面状態・値表示に異常はなかった。画面遷移中もタッチ取得間隔の最大は約5.1 msで、LVGL処理は最大約220 msだった。静止画面の描画転送も最初の5秒で29回まで減った。

microSDへの記録を伴う28秒間の計測も実施した。計測開始・記録・取消は成功し、SDエラーは0、電装出力はOFFのままだった。計測中のタッチ取得間隔の最大は約5.1 ms、LVGL処理の最大は約231 msだった。

シリアル操作では物理タッチの押下・解放は発生しない。実機の指でSettingsへの出入りと数字キーの入力を繰り返し、`perf`の`presses`と`delivered`が一致し、`overflow=0`であること、見た目に遅延や取りこぼしがないことを確認する。遅延が再発したら、直後に`perf`を送って表示された1行と、操作した画面・ボタンを記録する。`input_lag`は押下または解放の取得からLVGLへの配達までの最大値で、単位はµs。

今回の計測では、報告された「数秒」の事象そのものは再現していない。特定した入力停止と取りこぼし経路への対策が、実際の操作で効くかは指による確認が必要。
