# Delta Vega v2 UI仕様案

作成日: 2026-09-27  
推奨配置先: `docs/ui-spec.md`  
対象: M5Stack Tab5 / EEZ Studio / LVGL / PlatformIO  
状態: 実装に向けた仕様案。会話で合意した方針と、本書で追加した実装提案を区別する。

## 1. 目的と対象範囲

Hondaエコマイレッジチャレンジのドライバーが、速度・周回・残り時間・現在位置を短時間で把握できる車載画面を作る。走行中は主画面だけで必要な情報と操作が揃い、ページ切り替えや小さな操作を必要としない構成とする。

対象レースは7周を前提とする。大会の制限時間、正式な計測線、初回発進位置、最終ゴール位置は別途設定・確認する。画面のサンプル値を大会ルールとして固定しない。

本書は表示と操作、そのためのデータ境界を定義する。走行プランの解析・最適化は後回しとし、先にコース表示と車載UIを完成させる。将来の走行プランを受信・表示する場所と状態は確保する。

## 3. 合意済みの基本方針

- 1280×720、横向き。白基調、濃い文字、少ない装飾、大きな数値。
- 現在速度を最も目立たせる。平均速度、周回数、全体時間、ラップ時間も常時表示する。
- システムのハートビート、車速パルス入力、GPS状態を個別のインジケーターで示す。
- 地図に現在位置を表示する。将来はエンジンON/OFF地点と加速・惰性区間を重ねる。
- 初回の計測開始はドライバーのボタン操作。その後のラップ更新はGPSで自動化する。
- GPSによる周回の取りこぼしに備えて、走行中も大きな「手動ラップ＋1」ボタンを常設する。
- 重い解析は将来AWSで行う。Tab5は受信したプランを表示し、通信断でも計測・表示を継続する。
- コースはGPS対応の座標データを持ち、同じデータから生成した背景画像に動的要素を重ねる。

## 4. 画面構成

### 4.1 配置案

上部に状態表示、本文は「速度・周回」「時間」「コース」の3列構成とする。下記の座標は初期配置の提案であり、EEZでの見た目と実機での読みやすさに合わせて調整する。

| 領域 | 配置案（x, y, 幅, 高さ / px） | 内容 |
|---|---|---|
| 状態バー | 24, 16, 1232, 56 | HEARTBEAT、PULSE、GPS。将来は通信・プラン状態も小さく表示 |
| 左列 | 24, 96, 360, 480 | 現在速度、平均速度、現在周回 |
| 中央列 | 408, 96, 344, 480 | 全体の経過・制限・残り時間、当該周の経過・目標・残り時間 |
| 右列 | 776, 96, 480, 480 | コース地図、現在位置、走行プランの重ね描き |
| 左下操作 | 24, 600, 360, 96 | 走行中の「手動ラップ＋1」 |
| 中央下 | 408, 600, 344, 96 | 補正結果、GPS等の短い通知。通常は余白 |
| 右下 | 776, 600, 480, 96 | 開始前は「計測開始」。開始後は次のエンジン操作の案内 |

文字列を無理に横一列に詰めない。特に現在速度の単位は数値の下または右下、時間の経過値と目標値は別行にできる構成とする。

### 4.2 見た目と文字

- 白背景、本文は濃いグレー。区切りは薄いグレー、操作ボタンは青を基本とする。
- 現在速度は既存のRicty Diminished 160 pxを候補とする。平均速度・周回・経過時間は96 px前後、見出しは32〜48 px前後を起点に実機調整する。
- 既存の48/96/120/160 pxフォントは利用可能な候補であり、すべてを使う必要はない。追加サイズはEEZで必要な文字だけ生成する。
- 正常・異常やプランの状態は色だけでなく、短い文字・形状を併用する。
- 炎マークは専用の画像またはベクター由来のアセットを使う。絵文字フォントの有無に依存させない。
- 日本語ラベルを使う場合は必要な字形を生成対象に含める。開発中の英語ラベルとの混在は最終段階で整理する。
- 桁数が変わってもレイアウトが揺れない幅と配置にする。欠損を数値0で代用しない。

## 5. 表示項目と意味

| 項目 | 表示例 | 定義・挙動 |
|---|---|---|
| 現在速度 | `25.2 km/h` | 最新の有効な車速。未受信・古い値は`--.-`等で区別 |
| 平均速度 | `平均 24.6 km/h` | 計測開始からの走行距離÷経過時間。停止時間を含める案。距離の取得元は別途確定 |
| 現在周回 | `3 / 7` | 走行中の周回番号。内部の完了周回数とは分離する |
| 全体経過 | `12:34` | 手動開始イベントを起点とする経過時間 |
| 全体制限 | `制限 40:00` | レース設定値。ここに示す数値は表示例のみ |
| 全体残り | `残り 27:26` | 制限−経過。超過後は`超過 00:12`等を表示 |
| ラップ経過 | `02:18` | 現在ラップの開始イベントからの経過時間 |
| ラップ目標 | `目標 05:00` | プランまたは手動設定された当該周の目標所要時間 |
| ラップ残り | `残り 02:42` | 当該周の目標−経過。目標未設定時は`未設定` |
| 次の操作 | `次の始動まで 120 m` | 採用中プランに基づくコース沿いの前方距離。直線距離ではない |

ラップごとの「制限時間」は、現時点では運用上の目標として扱う。大会で定められた全体制限と混同させない。実際に周回別の公式制限がある場合は別フィールドとして設計する。

時間は原則`MM:SS`、1時間以上では`H:MM:SS`に対応できるようにする。`99:59`等への切り捨てや折り返しはしない。

**提案:** 画面表示用の時計はTab5の単調増加時刻を基準にする。通信受信時刻、GPS時刻、車載送信元の経過時間は区別する。既存ログで`timestamp_ms`と`total_time_ms`に差がある件は、将来の解析で別途解決する。コース形状には影響しない。

## 6. 状態と操作

### 6.1 画面状態

| 状態 | 時間・周回 | 左下 | 右下 |
|---|---|---|---|
| 開始待ち | 経過0、周回`— / 7` | 手動補正は無効 | 「計測開始」を表示 |
| 計測中 | 経過を更新、現在周回を表示 | 「手動ラップ＋1」を常設 | 次の操作。プラン未設定なら「プラン未設定」 |
| 完走 | 確定した結果を保持、周回は「完走」 | 手動補正は無効 | 「計測完了」 |

GPS未受信やクラウド未接続は「計測中」に重なる状態として扱い、通信異常だけで計測を停止しない。初期版はGPS未受信でも開始操作を許可する案とし、GPS自動ラップが利用できないことを表示する。

### 6.2 計測開始

- 明確な押下1回で開始する。開始操作と初回ラップ完了を混同しない。
- 開始時に完了周回数0、現在周回1、全体・ラップの経過0とする。
- 開始前に横切った計測線や開始ボタン直後の同じ線を、1周完了として誤認しない。
- 計測開始後は開始ボタンを次の操作案内へ切り替える。再押下でリセットされる動作は設けない。

### 6.3 GPS自動ラップ

- 指定された計測線を、指定方向に通過したイベントを使う。
- GPS位置の有効性・鮮度に加え、前回検出からの進行量・時間等を確認して二重検出を防ぐ。
- 基準経路の距離原点を跨いだだけで自動ラップが確定する仕様にはしない。
- 正式な計測線、初回スタートと最終ゴールの扱いは未確定。CSVから置いた距離原点は仮設定である。

### 6.4 手動ラップ補正

- 計測中は画面の同じ位置に大きな「手動ラップ＋1」を常設する。
- 取りこぼしたラップを素早く補正するため、毎回の確認ダイアログは出さない。
- タッチチャタリング・長押しによる連続加算を防ぐ。押して離す1操作につき1回を原則とする。
- GPSによる自動検出と近接した手動入力は同じ通過イベントとして照合し、二重加算を防ぐ。
- 手動入力が受理されたら「ラップ補正を反映」等の短い通知を表示する。

**補正時刻の扱いは実装提案:** 未確定のGPS通過候補が残っていればその時刻を採用する。候補がなければボタン操作時刻を暫定採用し、「手動・時刻概算」と記録する。後から押した時刻を実際の通過時刻と偽って扱わない。全体の経過時間は補正でリセットしない。

**未確定:** 誤操作の取り消し方法。短時間だけ「元に戻す」を中央下に出す案を候補とする。取消可能時間、連打抑制時間、自動検出との照合窓は実走行条件で決める。

### 6.5 完走と再計測

7周目の所定のゴール通過を確認した時点で完走とする。画面上の「7 / 7」になった瞬間は7周目開始であり、完走ではない。正式ゴールが周回計測線と同一かどうかは設定で明示する。

走行中に触れやすい場所へリセットボタンを置かない。再計測・停止・取り消しの詳細な操作は今後決める。デモ版での状態切り替えと実走行用の操作を混同しない。

## 7. インジケーター

| 表示 | 合意した目的 | 表示案・注意 |
|---|---|---|
| HEARTBEAT | システムの稼働確認 | 周期的に明滅。どの処理の生存を表すか明示する |
| PULSE | 車速計測パルスの入力確認 | 入力に合わせて点灯。人に見える最低点灯時間を設ける案 |
| GPS | GPSで位置を取得できるか | 有効かつ新しい位置は緑、無効・未受信・古い位置は文字付きで区別 |

単にLVGLタイマーで点滅させたハートビートを、車両側センサーや通信を含む「全システム正常」とは呼ばない。UI更新・車載データ受信等、監視対象を先に定める。

PULSEの最低点灯時間は表示上の処理であり、実際のパルスカウントと分離する。高頻度入力で連続点灯に見えることは許容し、LED点滅回数を測定値として扱わない。

**将来追加の提案:** 状態バーに小さな「通信」「プラン」状態を追加し、GPS状態と混同させない。

| JSON | `motegi_course.json` |
| 背景画像 | `motegi_background_480.png`、480×480 px、北が上 |

画像とJSONは同じ版の組み合わせで使用する。道路幅14 px相当の描画は見やすさのための表現で、実際の道路幅や走行可能範囲を示さない。

### 8.2 座標変換

`coordinate_system`の原点・係数を使い、緯度経度から東・北のメートル座標へ変換する。

```text
east  = (longitude - origin_lon_deg) * east_m_per_lon_deg
north = (latitude  - origin_lat_deg) * north_m_per_lat_deg

x = M[0][0] * east + M[0][1] * north + M[0][2]
y = M[1][0] * east + M[1][1] * north + M[1][2]
```

`M`はJSONの`render.local_to_pixel_matrix_2x3`。得られた画像内座標に画面内の画像配置位置を加える。画像の拡縮・回転を変更する場合は、オーバーレイにも同じ変換を適用する。緯度経度の差分はdouble精度で計算する。

### 8.3 重ね描き

下から順に、コース背景、加速・惰性区間の線、エンジン操作地点、現在位置、状態表示を重ねる。

| 要素 | 表現 |
|---|---|
| 現在位置 | 背景やプランの線と区別できる濃色の矢印 |
| エンジンON | 炎のマーク、必要に応じて`ON` |
| エンジンOFF | 停止を表す四角等のマーク、必要に応じて`OFF` |
| 加速区間 | オレンジの線 |
| 惰性区間 | 青い線 |

これらを背景画像に焼き込まない。プラン未設定の場合は背景と現在位置のみ表示し、サンプルの火のマークを実際の指示として残さない。

通常はGPS位置を基準経路の近傍線分へ投影して表示する案とする。ただし大きく離れた位置や不正なジャンプを無条件に経路へ吸着させない。初期実装では生GPS表示から始め、投影の採用距離・進行チェックは検証後に設定する。

低速・停止時はGPS差分だけで矢印が回転しないよう、最後に信頼できた方向を保持するか方向なしの点に切り替える。GPSが古いときは最終位置を淡色・「位置更新なし」で示し、最新位置と誤認させない。

コース上の地点は原則として基準原点からの距離`s_m`で管理する。最終点と先頭点を結ぶ線分も補間対象に含める。同じ地点でも周回番号が違えば別の指示になり得るため、プランでは対象周回も保持する。

## 9. 将来の走行プラン表示

### 9.1 受信する内容

AWSで基準プランと周回ごとの補正を作り、Tab5では採用済みプランを表示する。初期版は通信・解析なしでも、模擬データでUIを確認できるようにする。

UIが扱う情報の案:

- レースID、コースID・版、基準プランID、更新番号。
- 対象周回、適用可能な期限またはコース上の適用区間。
- 周回目標時間、エンジンON/OFFの予定地点、速度条件、加速・惰性区間。
- 変更理由の短い説明と、受信済み・採用済み・不採用の状態。

地図上の予定地点と、速度条件による実際の操作タイミングを区別する。速度しきい値が主条件の場合、マークは予定位置として扱い、条件を満たしていないのに「今すぐ始動」と表示しない。詳細な指示判定は解析実装時に定義する。

### 9.2 更新・通信断

- プラン見直しは原則1周ごととし、通常は周回途中で頻繁に表示を変えない。
- 受信しただけで地図を更新せず、対象レース・コース・周回・版・期限を検証してから採用する。
- 周回直後に届く更新の適用締切は別途定義する。締切後に届いた指示を遡って採用しない。
- 同じ更新の重複受信や古い更新で、表示を巻き戻さない。
- 通信断でも最後に採用した有効なプランまたは保存済み基準プランを表示する。利用できるプランがなければ「プラン未設定」とする。
- 有効な指示をキャッシュ表示している状態と、期限切れで使えない状態を区別する。
- 表示側で採用した版をシステム側へ通知できる設計とする。プランの確認操作を走行中のドライバーに毎回要求しない。

参考となる合意済み戦略は「最終盤の不要な再始動を避けて惰性でゴールを通過する」「ペースが速い場合は早めにOFF」「遅い場合はONの速度しきい値を上げて惰性を短縮する」。具体的なしきい値・補正量をUIにハードコードしない。

## 10. 表示と機器処理の境界

EEZはレイアウト・固定スタイル・静的アセットの編集元とする。ラップ判定、時間計測、通信、状態管理、動的な地図描画とイベント登録は生成コードの外に実装する。

### 10.1 配置案

| 配置先 | 役割 |
|---|---|
| `docs/ui-spec.md` | 本書。UI仕様の参照元 |
| `eez/delta-vega-v2.eez-project` | 画面の編集元。既存 |
| `eez/fonts/` | 元フォントとライセンス。既存 |
| `assets/courses/motegi_oval_2025_gps_v1/` | コースJSON・PNG・SVG・必要なら生成スクリプト。新設案 |
| `src/ui/` | EEZ生成物。既存。生成先は`../src/ui`を維持 |
| `src/app/ui_presenter.*` | 表示モデルからLVGLオブジェクトへの反映と操作イベント登録。新設案 |
| `src/app/race_state.*` | 計測・周回・補正状態の管理。新設案 |

| 案内 | `next_action_label`, `notice_label` |

### 10.3 データと更新

表示モデルには値だけでなく、有効性、最終更新時刻、取得元を保持する。主な入力は速度、走行距離、位置、GPS状態、パルス到来、レース状態、プラン状態とする。エンジンON/OFFの実測値は現在のログに含まれないため、速度から確定的に推測して実測状態として表示しない。

**更新周期の初期提案:** 数値・地図は5〜10 Hz程度、秒表示の文字更新は1 Hz。受信・パルス計測・時間管理は描画とは独立させる。実際の入力レート以上に位置を新しく見せない。

LVGLオブジェクトへの変更はUI処理の実行文脈に集約する。通信処理や割り込みから直接UIを書き換えず、状態やイベントを受け渡す。EEZ再生成後もイベント登録・表示更新が保たれる構成にする。

## 11. 実装順序

1. **静的レイアウト:** 白基調の3列構成、速度単位修正、必要なラベルとボタンを配置。
2. **コース表示:** 背景画像と固定位置マークを表示し、JSONの座標変換と一致させる。
3. **模擬データ:** 値・状態・開始・手動補正の表示遷移を、通信なしで確認。
4. **実データ:** 車速・GPS・パルス・鮮度表示と時間計測を接続。
5. **自動ラップ:** 正式計測線を設定し、重複抑制・手動補正・完走判定を検証。
6. **プラン表示:** 模擬プランの重ね描き、受信・版管理・通信断時の挙動を実装。

走行解析・最適化は別作業とする。UIの完成をAWS解析の完成待ちにしない。

## 12. 受け入れ条件

- 1280×720で文字・ボタン・地図が重ならず、速度と残り時間が車内から読み取れる。
- 速度単位が`km/h`。全体制限と周回目標が明確に区別される。
- 開始前に「計測開始」があり、開始後も「手動ラップ＋1」が常時見える。
- 開始操作だけでラップ完了が加算されない。7周目開始と完走を区別する。
- 手動補正1操作で1回だけ反映され、同じ通過のGPS検出と二重加算しない。
- 全体時間はラップ更新・補正でリセットされない。制限超過は負数や折り返しではなく超過として表示される。
- 欠損・古い車速・GPS位置を正常な最新値として表示しない。
- 地図上の複数地点（両直線・両コーナー）でGPS位置と背景が一致する。画像の移動・拡縮後もずれない。
- 現在位置、ON/OFF地点、区間色を個別に更新できる。
- プラン未設定時に架空の操作指示を出さない。通信断でも時間・車速・GPS表示と手動操作が継続する。
- 古い・重複・期限切れのプランが表示を巻き戻さない。
- EEZで再生成してもアプリ側の操作・更新処理が失われない。

## 13. 実装前または実機評価で確定する事項

| 項目 | 現時点の扱い |

| 車速・GPS入力仕様 | 通信経路、単位、時刻、更新レート、有効性を確定 |

| 書体・字形・日中視認性 | 実機で確認し、サイズ・コントラストを調整 |
