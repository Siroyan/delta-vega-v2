# MQTTテレメトリのデータ仕様

Tab5は、最新の1メッセージだけで現在の走行情報と、その計測で確定した全ラップタイムが分かるJSONを送信する。ピット側で受信履歴を蓄積したり、周回更新時刻を逆算したりする必要はない。

## 接続・送信タイミング

- 接続先・機体ID・メモは`config/network_secrets.h`で指定する。トピックの設定例は`v0/delta_machine_alpha/telemetry/racing_data`。
- QoSは0、retainは無効。送信処理はネットワークタスクで行い、UI・計測・GPIO制御を通信待ちにしない。
- 起動後のWaiting、計測開始、計測取消、完走時の最新状態を送信対象にする。計測中は約500ms周期で更新する。
- 未接続でも最新状態を保持し、MQTT接続・再接続時に送信する。途中のサンプルを順番に再送する方式ではない。
- 計測中のサンプルは1500ms以上古ければ送らず、次の新しいサンプルを待つ。完走結果と取消後のWaitingはこの期限で破棄しないため、通信断中に完走・取消した場合も復旧後に送信できる。
- 接続ごとの世代番号を送信タスク内部で管理し、短い切断・再接続でも最新状態を再送する。この番号はJSONには含めない。
- QoS 0のため各メッセージの受信保証はない。完走後の定期送信は行わず、完走時と再接続時に送信する。

## JSON項目

| 項目 | 型・単位 | 意味 |
|---|---|---|
| `speed` | 数値 / km/h、または`null` | 車輪パルス由来の現在速度。設定された区間数で平滑化する |
| `average_speed` | 数値 / km/h、または`null` | 計測開始からの平均速度。停止時間も含む |
| `lap_number` | 整数 | 現在の周回番号。Waitingでは0、計測開始時は1 |
| `total_time_ms` | 整数 / ms | 計測開始からの経過時間。完走時に固定する |
| `lap_time_ms` | 整数 / ms | 走行中の周回の経過時間。完走後は最終周の確定タイム |
| `latitude` / `longitude` | 数値 / 度、または`null` | 新鮮なGPS測位の緯度・経度 |
| `timestamp_ms` | 整数 / ms | この状態を取得した時点のTab5起動後の経過時間。UTC・NTP時刻ではない |
| `machine_id` | 文字列 | 設定された機体ID |
| `memo` | 文字列 | 設定されたメモ |
| `completed_lap_times_ms` | 整数の配列 / ms | 現在の計測で確定したラップタイム。先頭が1周目、以降は周回順 |

従来の10項目の名前・型・意味を維持し、`completed_lap_times_ms`を追加する。未取得・無効な速度や位置は`null`になる。

### 3周目を走行中の例

```json
{
  "speed": 24.5,
  "average_speed": 22.1,
  "lap_number": 3,
  "total_time_ms": 765000,
  "lap_time_ms": 45000,
  "latitude": 36.532766,
  "longitude": 140.226269,
  "timestamp_ms": 865000,
  "machine_id": "delta_machine_alpha",
  "memo": "Delta Vega v2",
  "completed_lap_times_ms": [362000, 358000]
}
```

1周目が6分02秒、2周目が5分58秒。未完了の3周目は配列に含めず、現在の45秒を`lap_time_ms`で表す。

## ラップ履歴の扱い

- 初期状態と計測開始直後は`[]`。
- GPS自動周回・手動LAPのどちらでも、受理された更新時刻までの周回時間を計測ドメインで確定する。拒否された操作では追加しない。
- 計測中の配列要素数は`lap_number - 1`。自動・手動ゴールでは最終周も追加し、完走後はコースの周回数と一致する。重複ゴールでは追加しない。
- 各値は区間のラップタイムであり、スタートからの累積通過時刻ではない。完走時は配列の合計が`total_time_ms`と一致する。
- 取消時は履歴・周回番号・経過時間をクリアしたWaiting状態を送信対象にする。取消後に開始した計測へ前回の履歴を引き継がない。
- 完走後はRAMに履歴を保持し、接続復旧時も全履歴を送る。`timestamp_ms`は送信し直した時刻に置換せず、保持した状態の取得時刻を表す。
- 最大100周。再起動後の履歴復元と、ピット側で計測IDを用いた履歴管理は今回の実装に含めない。

## メモリ・SD記録

履歴は最大100件の64bit整数と有効件数を持つ固定長の値としてSnapshotへ格納する。動的コンテナをFreeRTOSキューにバイトコピーする構成にはしない。MQTTの待ち合わせには最新1件だけを使う。

ESP32-P4向けビルドでSnapshotは440→1248バイト、SD記録のRecordは456→1264バイトになる。Snapshot用2キューと48件のSD記録キューのデータ領域は合計40,400バイト増える。画面向けの最新Snapshotキューは従来どおり約10ms周期で更新し、UIは約100ms周期で参照する。キューの件数は増やさない。

コンパイラのスタック使用量と呼び出しの重なりを確認し、計測タスクとSDタスクは8KiB→12KiBに拡張した。ネットワークタスクは8KiBを維持する。これは静的な余裕の確認であり、実機のスタック最小残量と内部DMAヒープは結合・長時間試験でも確認する。

MQTTのJSONバッファは`kTelemetryJsonCapacity`（3124バイト）、GPS診断を含むSDサンプルは`kSessionSampleJsonCapacity`（3636バイト）。100件すべてを64bit整数の最大桁数で表しても収まる容量とし、不足時は不完全なJSONを送信・保存せずエラーにする。大きい文字列バッファは各ワーカー専用の固定領域に置く。

SDの通常サンプルにも同じラップ配列が入り、従来のGPS診断項目も維持する。セッションのメタデータとイベント行の形式は変更しない。取消直前のSD記録は、取り消した計測の記録として保持する。

## 検証範囲

`test/native/core_tests.cpp`で、ラップ履歴の確定・クリア・完走後保持、GPSと手動の計測、100周とJSON容量、通信状態を模擬した再接続・送信失敗後の再試行を確認する。実行方法は[test/README.md](../test/README.md)を参照。

ネイティブ試験は実際のAWS IoT接続、Wi-Fi断、USBの停滞、実機のタスク余裕を直接検証するものではない。実機・AWSでの結合試験と長時間評価は別途行う。

### 2026-10-23の実装検証

- `python3 scripts/test_native.py`：既存テストと、履歴・JSON・再接続方針の追加3テストがASan／UBSan付きで成功。
- `pio run -e esp32p4_pioarduino`：ファームウェアのビルド成功。静的RAMは66,636バイト、プログラムサイズは2,794,897バイト。これには起動後のキュー・タスク・ネットワーク用ヒープ確保は含まれない。既存の`esp-idf-size --ng`オプション警告は残るが、PlatformIOの容量確認とバイナリ生成は成功。
- 差分レビュー：ラップの確定境界、取消・重複操作、再接続世代、固定長キュー、JSON容量を確認。Snapshotの拡大に伴うスタック不足のリスクを修正し、再ビルド・再テストした。
- Tab5へ書き込み、ハッシュ照合成功。続く45秒のシリアル監視でWaiting画面の起動、Port.AのGPS受信約4.9Hz、SD利用可能・エラー0、Wi-FiとMQTTの接続を確認。電装・点火出力はLOWで、監視中にpanic・assert・追加の再起動はなかった。
- MQTT接続後の確認時点で内部DMA空き236,676バイト、最大連続空き229,364バイト。実機のスタック最小残量、AWSでのJSON内容・ラップ履歴の受信、通信断・長時間走行は未検証。
